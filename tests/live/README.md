# Live Quire API tests

These tests hit the **real Quire API** at `quire.io` (or your configured server)
using a real OAuth access token. They verify that `QuireClient` works end-to-end
against the live contract — endpoint paths, request/response shapes, status
codes, error envelopes.

They are **opt-in**. Every `describe` is wrapped in
`describe.skipIf(!hasTokens)`, so without a configured env file the whole
folder cleanly no-ops and `npm test` stays offline / CI-safe.

## Quick reference

```bash
# All offline tests (mocked unit tests under src/__tests__/) — safe, fast, CI-default
npm test

# All live tests — opt-in, runs against the real Quire API
npm run test:live

# One file
npx vitest run --project live tests/live/task.live.test.ts

# One test by name (vitest -t matches a substring of "describe > test name")
npx vitest run --project live tests/live/task.live.test.ts -t "T1 "

# Bootstrap / refresh the test token (browser OAuth flow)
npm run test:live:prepare
```

## Prerequisites

1. A Quire OAuth app you control, with `http://localhost:8000/callback`
   registered as a redirect URI. (The same app the production caller uses is
   fine — the live tests are scoped to a dedicated test project, not the
   production data.)
2. A dedicated test project named `Quire_API_Test_Project` in a workspace the
   authorized user belongs to. Several tests assume specific custom-field
   definitions live on it:
   - `Cost` (Currency)
   - `Work time` (Duration)
   - `Note` (Paragraph)
3. (Optional) A second project at `Test_Transfer_Project` in the same workspace
   for the cross-project transfer tests.
4. (Optional) Free-plan org / project anchors for the subscription / plan-
   gating tests (`QUIRE_TEST_FREE_ORG_ID`, `QUIRE_TEST_PAID_ORG_ID`,
   `QUIRE_TEST_FREE_PROJECT_ID`).

## First-time setup

The entire live-test config — OAuth-app creds, access/refresh tokens, test
project anchors — lives in **one env file**. Both the tests and the bootstrap
script read it from the same place; the script also writes back to it.

There's no separate root-of-repo `.env`, no global config, no interactive
prompt. The flow below is one-time per machine.

### Step 1 — Create the env file with your OAuth-app creds

The file is resolved in this order — the first one that exists wins:

1. `tests/live/.env` inside the current checkout (per-checkout opt-in)
2. `~/.config/quire/test-api.env` (**canonical** — recommended)
3. `~/.config/quire-mcp/test-api.env` (transitional fallback for the legacy
   path; used by [quire-mcp]'s mirror live test too)

The canonical home-dir path is the right choice for most setups — every fresh
clone of `quire-api-client` (and every worktree of `quire-mcp`) inherits the
same tokens without re-running OAuth.

```sh
mkdir -p ~/.config/quire
cat > ~/.config/quire/test-api.env <<'EOF'
QUIRE_API_SERVER=https://quire.io
QUIRE_CLIENT_ID=<from your Quire OAuth app>
QUIRE_CLIENT_SECRET=<from your Quire OAuth app>
EOF
```

You need a Quire OAuth app you control, with `http://localhost:8000/callback`
in its registered redirect URIs (so the bootstrap script can receive the
authorization code on `localhost:8000`).

### Step 2 — Run the OAuth bootstrap

```bash
npm run test:live:prepare
```

What it does:

1. **Reads** `QUIRE_API_SERVER`, `QUIRE_CLIENT_ID`, and `QUIRE_CLIENT_SECRET`
   from the env file you just created. If any of those three are missing it
   exits with a "Missing X — seed the file with …" message and stops.
2. Opens a browser to Quire's OAuth consent screen for your client id.
3. Listens on `http://localhost:8000/callback` for the redirect-back code.
4. POSTs the code to `${QUIRE_API_SERVER}/oauth/token`, gets back
   `access_token` + `refresh_token` + `expires_in`.
5. Looks up the test project's OID and the workspace OID via
   `GET /project/id/Quire_API_Test_Project` (a project named exactly that
   must exist in a workspace the authorizing user belongs to).
6. **Writes** the file back in place. Your three input creds are preserved;
   the previous file is backed up to `<file>.bak`.

> **Where does `test:live:prepare` get the client id?** From the env file in
> step 1 — that's the only source. There's no hardcoded id, no CLI flag, no
> fallback. If you have multiple Quire OAuth apps, swap the file's
> `QUIRE_CLIENT_ID` / `QUIRE_CLIENT_SECRET` and re-run prepare.

After step 2, the env file looks like this:

```sh
# Generated by scripts/prepare-test-tokens.ts — DO NOT COMMIT.
QUIRE_API_SERVER=https://quire.io
QUIRE_CLIENT_ID=...
QUIRE_CLIENT_SECRET=...
QUIRE_TEST_ACCESS_TOKEN=...
QUIRE_TEST_REFRESH_TOKEN=...
QUIRE_TEST_EXPIRES_AT=1700000000000
QUIRE_TEST_PROJECT_ID=Quire_API_Test_Project
QUIRE_TEST_PROJECT_OID=oid_...
QUIRE_TEST_ORG_OID=oid_...
# Optional — used by subscription.live.test.ts + project.live.test.ts.
# Leave blank to skip those cases.
QUIRE_TEST_FREE_ORG_ID=
QUIRE_TEST_PAID_ORG_ID=
QUIRE_TEST_FREE_PROJECT_ID=
```

### Step 3 — Run the tests

```bash
npm run test:live
```

`QuireClient` auto-refreshes the access token on its 5-minute pre-emptive
window (and on any mid-suite 401), so a single `test:live:prepare`
invocation holds for as long as the **refresh** token stays valid. Quire's
refresh tokens don't rotate and are long-lived until you revoke the app in
Quire's UI — most maintainers run prepare once and forget about it.

If you ever revoke the app — or want to start from a clean slate — re-run
`test:live:prepare`. The script preserves your creds and rewrites only the
tokens.

[quire-mcp]: https://github.com/quire-io/quire-mcp

## Run patterns

| What you want | Command |
|---|---|
| All offline (mocked) tests | `npm test` |
| All live tests | `npm run test:live` |
| One live file | `npx vitest run --project live tests/live/<file>.live.test.ts` |
| One test by name | `npx vitest run --project live tests/live/task.live.test.ts -t "T1 "` |
| A test group by prefix | `npx vitest run --project live tests/live/task.live.test.ts -t "T17"` (matches T17, T17b, T17c) |

The trailing space in `-t "T1 "` matters — without it the substring match also
catches T10, T11, T1b, etc.

## Conventions

- **Pattern**: tests prefer `liveClient().method()` for happy paths (so the
  test exercises both the API contract and the `QuireClient` wrapper). They
  fall back to `rawApi(...)` for:
  - explicit status-code assertions (the wrapper throws on non-2xx, which
    hides the status)
  - URL-shape variants the client deliberately doesn't expose
    (`/task/id/{projectId}/{taskId}`, `/comment/attach/id/…`, etc.)
  - endpoints not yet wrapped by `QuireClient`.
- **Naming**: every resource created during a test uses the `runTag` prefix
  exported from `helpers.ts` (e.g. `live-test-1700000000000`), so leftover
  objects from a failed run are easy to spot and clean.
- **Cleanup**: each test owns its fixtures and tears them down in `afterAll`.
  `afterAll` runs even when tests fail, so leftover state shouldn't accumulate
  across runs.
- **Rate limits**: Quire rate-limits aggressively. `helpers.ts`'s `rawApi`
  retries on 429 with exponential backoff up to a 60-second cap. The vitest
  config (`vitest.config.ts`) runs the `live` project with
  `fileParallelism: false` — concurrent files burst the limiter; serial
  execution keeps it sustainable.
- **Quota awareness**: the full live suite issues hundreds of requests. If
  you're iterating on one test, run it in isolation rather than the whole
  folder.

## Two-token model in `helpers.ts`

`liveClient()` returns a singleton `QuireClient` per test file with two hooks
wired up:

1. `refreshTokens` callback (via the public `refreshTokens` helper from this
   package) — so a 401 mid-suite auto-refreshes and the next call succeeds
   without manual intervention.
2. `onTokenRefresh` callback that updates a module-local "current access
   token" cache. `rawApi` reads from that cache, so post-refresh raw calls
   use the freshly-rotated token instead of the now-invalidated value still
   sitting in the env file.

If you write a new live test, just import `liveClient()` and `rawApi()` from
`./helpers.js` — token rotation handles itself.

## Adding new tests

1. Pick the right file (or create a new `<resource>.live.test.ts` for a new
   resource).
2. Wrap your `describe` in `describe.skipIf(!hasTokens)` so the suite stays
   offline-safe.
3. Use `liveClient()` for normal calls; `rawApi()` only when the wrapper
   would obscure the assertion (status code, error body) or when the
   endpoint isn't on `QuireClient` yet.
4. Name every created resource with the `runTag` prefix.
5. Tear down in `afterAll`.

See `task.live.test.ts` as the canonical pattern.
